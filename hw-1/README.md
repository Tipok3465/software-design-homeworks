# Домашнее задание 1: ВышКат

Консольное приложение для учёта парка кикшеринга. Оно принимает транспорт
только после техосмотра, ведёт единый инвентарный список транспорта и вещей,
считает суточное энергопотребление и формирует список техники для новичков.

## Установка и запуск

Требуется Python 3.10 или новее.

```bash
python3 -m venv .venv
.venv/bin/pip install -e '.[dev]'
.venv/bin/python -m sd_hw_1.cli
```

После установки также доступна команда:

```bash
.venv/bin/sd-hw-1
```

Приложение откроет интерактивное меню. Через него пользователь может принять
транспорт, добавить вещь на баланс и запросить каждый предусмотренный заданием
отчёт. Данные вводятся пользователем и хранятся в памяти до выхода из программы;
заранее заданных объектов в рабочем коде нет.

## Тесты

```bash
.venv/bin/pytest
.venv/bin/ruff check .
```

`pytest` автоматически измеряет покрытие и завершится с ошибкой, если оно ниже
60%.

## Устройство проекта

- `domain/interfaces.py` - небольшие интерфейсы инвентаризируемого объекта,
  потребителя энергии и техосмотра.
- `domain/vehicles.py` - базовый транспорт, электрический транспорт и его виды.
- `domain/equipment.py` - вещи на балансе и энергопотребляющее оборудование.
- `services/service_center.py` - правило допуска транспорта по результату осмотра.
- `services/fleet.py` - прием транспорта, учет, отчеты и правило для новичков.
- `container.py` - место сборки конкретных зависимостей.
- `cli.py` - интерактивный консольный интерфейс.
- `tests/` - тесты предметной модели и поведения приложения.

Данные намеренно хранятся в памяти: база данных и репозитории не нужны для
заданных сценариев и усложнили бы решение без пользы для предметной модели.

## SOLID

### Single Responsibility Principle

Сущности в `domain` проверяют только собственные инварианты. `ServiceCenter`
решает только вопрос допуска транспорта. `FleetService` выполняет сценарии
учёта, а `cli` отвечает только за ввод и вывод. Поэтому изменение интерфейса
взаимодействия не затрагивает техосмотр и предметные сущности.

### Open/Closed Principle

`FleetService` работает с базовым `Vehicle` и интерфейсами. Новый вид транспорта
добавляется наследованием от `Vehicle` или `ElectricVehicle`; изменять сервис
парка не требуется. Это отдельно проверяет тест
`test_new_vehicle_type_requires_no_fleet_service_changes`.

### Liskov Substitution Principle

`Scooter`, `Bicycle`, `ElectricBicycle` и пользовательские виды транспорта могут
передаваться во все операции, принимающие `Vehicle`. Подклассы не усиливают
предусловия метода приёмки и сохраняют инварианты базового класса.

### Interface Segregation Principle

`InventoryItem` и `EnergyConsumer` разделены. Шлем и обычный велосипед имеют
инвентарный номер, но не получают фиктивное свойство энергопотребления.
Электросамокат, электровелосипед, док-станция и зарядный шкаф структурно
реализуют оба нужных интерфейса.

### Dependency Inversion Principle

`FleetService` зависит от `VehicleInspection`, а не от `ServiceCenter`.
Конкретная реализация подключается в `container.py`. В тестах она заменяется
объектом `Mock`, который принимает или отклоняет транспорт независимо от
реального сервисного центра.

Наиболее явно выражен **DIP**: решение техосмотра является внешней зависимостью
сервиса парка, и его подмена проверяется тестами.

## Ограничения SOLID

Принцип OCP сознательно ограничен в правиле отбора транспорта для новичков. Порог `beginner_friendliness >= 6` задан непосредственно в методе `FleetService.beginner_vehicles()`. Чтобы изменить это правило, потребуется изменить метод сервиса.

Для одного фиксированного правила отдельная стратегия добавила бы лишние классы и усложнила проект. Если появятся разные правила для разных категорий пользователей, отбор можно вынести в отдельный интерфейс и передавать его реализацию через конструктор.

Также при добавлении нового вида транспорта потребуется дополнить меню в `cli.py`. При этом логика учета и отчетов в `FleetService` останется прежней.

## Использование ИИ

ИИ использовался в проекте как вспомогательный инструмент:
+ для проверки соответствия заданию и исправления обнаруженных ошибок
+ для обсуждения структуры и помощи оформления README
+ для обсуждения вариантов реализации архитектуры

## Как система расширяется

- **Новый вид транспорта:** создать подкласс `Vehicle` либо `ElectricVehicle`.
  Сервис парка и его отчёты менять не потребуется.
- **Сотрудник:** сотрудник не является объектом на балансе по текущим правилам.
  Для него следует создать отдельный модуль и сервис.
- **Склад запчастей:** добавить сущность запчасти и отдельный складской сервис.
  Если запчасти ставятся на общий баланс, они реализуют `InventoryItem`; иначе
  транспортный учёт остаётся неизменным.

## Какие тесты фиксируют ключевые решения

- `test_approved_vehicle_is_added` и `test_rejected_vehicle_is_not_added`
  фиксируют обязательный техосмотр и его подмену через DI.
- `test_service_center_accepts_vehicle_on_threshold` фиксирует границу допуска.
- `test_beginner_rule_includes_boundary_value_six` фиксирует правило для
  новичков.
- `test_total_energy_includes_consumers_only` проверяет сумму энергии без
  фиктивного потребления обычных вещей и велосипеда.
- тесты в `test_application.py` передают пользовательский ввод через функцию и
  проверяют приём транспорта, отказ техосмотра, добавление вещи и все виды отчёта.
