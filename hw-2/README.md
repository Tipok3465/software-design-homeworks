# ДЗ2: Преподавательская оценка студентов

Это консольная ведомость для одного курса. В ней можно добавить студентов,
задать критерии оценивания, выставить оценки и посчитать итог. Если оценка
введена неправильно, её можно исправить или отменить. Итог можно выгрузить в CSV.

При первом запуске ведомость пустая. Данные сохраняются между запусками.

## Установка и запуск

Нужен Python 3.10 или новее. Команды нужно выполнять из каталога `hw-2`:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -e '.[dev]'
.venv/bin/sd-hw-2
```

По умолчанию ведомость сохраняется в `pos-gradebook.json` в текущем каталоге.
Другой файл можно выбрать через `--data`. CSV создаётся по пути, введённому в
меню; существующий файл не перезаписывается.

## Как устроена ведомость

У студента (`Student`) есть код и имя. Код уникален, а имена могут совпадать.
У критерия (`Criterion`) есть свой код, название, максимальный балл и вес.
Оценка (`Evaluation`) связывает студента с критерием и хранит балл (`Score`).

Студент и критерий — сущности: в ведомости они определяются по коду.
`Score` — неизменяемый объект-значение: два балла с одинаковым числом равны.
Отрицательные баллы, `NaN` и бесконечность не принимаются. Максимум и вес
критерия ограничены диапазоном от `0.000001` до `1000000` включительно.
Это технические границы приложения для работы с `Decimal`, а не правило
оценивания курса.

Всеми изменениями управляет `Gradebook`, корень агрегата. Он проверяет,
что студент и критерий существуют, а оценка не превышает максимум.
Повторно выставить оценку за тот же критерий нельзя — для этого есть
отдельная операция исправления. Если новый балл не прошёл проверку,
старая оценка остаётся. Отмена удаляет оценку.

## Как считается итог

Расчёт вынесен в доменный сервис `FinalScoreCalculator`. Он использует
критерии и текущие оценки, а результат возвращает в `FinalScore`.
Отдельно сохранять итог не нужно: после исправления оценки он пересчитывается.

Формула:

```text
100 * sum(балл / максимум * вес) / sum(весов)
```

Веса относительные, их сумма не обязана быть равна 100. Например, в сценарии
выше практика даёт `8 / 10 * 2`, теория — `15 / 20 * 3`.
Получается `100 * (1.6 + 2.25) / 5 = 77`.

Есть два режима:

- Предварительный: пропущенные оценки дают нулевой вклад, но веса этих
  критериев остаются в знаменателе. В примере без теории получится 32.
- Официальный: нужны оценки по всем критериям. Если чего-то не хватает,
  приложение перечислит пропуски.

Если критериев ещё нет, итог посчитать нельзя. Для расчётов используется
`Decimal`; в консоли и CSV итог выводится с двумя знаками после точки.

## Где что лежит

В проекте используется Ports and Adapters: правила оценивания отделены
от ввода и хранения данных.

- `domain/` — студенты, критерии, ведомость и расчёт итога.
- `application/` — `PosApplication` со сценариями работы и интерфейсы
  `GradebookRepository` и `ResultExporter` для хранения и экспорта.
- `adapters/` — консольное меню, хранение в JSON и выгрузка в CSV.
- `main.py` — запуск приложения и сборка зависимостей в `Container`.

Зависимости направлены от адаптеров к приложению и домену. Домен ничего
не знает о файлах и меню. `PosApplication` получает репозиторий, экспортёр
и калькуляторы через конструктор — это DI. В тестах вместо файлового
хранилища и CSV можно передать тестовые реализации.

После успешного изменения ведомость сохраняется. При загрузке JSON оценки
снова проходят через методы `Gradebook`, так что вручную записанный в файл
балл выше максимума тоже будет отклонён. Сохранение идёт через временный файл
с последующей заменой ведомости.

## Паттерны

Создание оценки собрано в `Evaluation.create()`: метод принимает студента,
критерий и балл, проверяет максимум и возвращает оценку. Его используют
и выставление, и исправление. Это простой фабричный метод, а не GoF
Factory Method с выбором реализации через подклассы.

`PosApplication` работает как фасад (Facade). Например, для экспорта меню
передаёт код студента, режим и путь. Загрузка ведомости, расчёт и вызов
экспортёра уже происходят внутри фасада.

Правило обработки пропусков реализовано через стратегию (Strategy).
`AllowMissingScores` разрешает расчёт с пропусками, а `RequireAllScores`
отклоняет его. Обе политики передаются в калькулятор через конструктор,
поэтому формулу для каждого режима дублировать не приходится.

## Проверки

```bash
.venv/bin/python -m pytest -q
.venv/bin/ruff check .
```

В `test_gradebook.py` проверяются ограничения ведомости и изменение оценок,
в `test_results.py` — формула и оба режима. `test_application.py` проверяет
сценарии с тестовым хранилищем и экспортёром, а `test_adapters.py` — работу
через меню, сохранение после перезапуска и содержимое CSV.

## Ограничения

Приложение рассчитано на один курс и один процесс. Студентов и критерии
можно добавлять и просматривать; их редактирование, удаление, пересдачи и
апелляции не реализованы. Изменять и отменять можно сами оценки.

## Использование ИИ

ИИ использовался для разбора ТЗ, проверки кода и поиска ошибок,
а также для проверки точности описания архитектуры.
